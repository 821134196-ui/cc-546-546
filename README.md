# 餐厅催/退/重做协同系统

前厅服务员记录客人**催菜、退菜、要求重做**，全部关联原订单项与当前制作阶段；后厨在处理单上回复已备料/烹制中/已出餐；值班经理审批退款与费用。纯 Python 标准库 + SQLite，零三方依赖。

## 启动

```bash
python3 run.py            # 重建演示数据（含错上桌案例）并启动 → http://localhost:8000
python3 run.py --port 8080 --keep-db
```

- 前厅 http://localhost:8000/floor —— 按桌号，突出最大等待时长（<5 分钟绿 / <10 分钟琥珀 / ≥10 分钟暖红）
- 后厨 http://localhost:8000/kitchen —— 按档口，重做菜在**原桌号/客位**位置显示红色「重做·第 N 版」
- 值班经理 http://localhost:8000/manager —— 待审批 + 费用台账（金额与原因紧邻）

右上角切换身份：1 小王(服务员)、2 小李(服务员)、3 张大厨(后厨)、4 陈经理。页面每 3 秒轮询。

## 业务规则

| 场景 | 责任 | 处理与费用 |
|---|---|---|
| 连续催菜 | 后厨 | 同一原项只一条催单，重复催单追加时间线，**绝不重复入后厨队列** |
| 错上桌 | 前厅 | 菜标 `wrong_delivered`，不向客人收费，错菜计内部损耗 |
| 过敏提醒漏看 | 下单备注了→后厨；没记→前厅 | 已出餐，全额退款（需经理审批） |
| 温度不合格 | 后厨 | 重做：原项冻结，新菜按原单位置入队，重做成本内部核算 |
| 客人临时离席 | 客人 | 未开火直接取消免单；已开火保留收费须经理审批 |
| 退菜时已出餐 | 按原因 | 仅已出餐可全额退款；经理批准后模拟支付退款 + 打印凭证 |

- 服务员只能**发起**退款/收费/重做申请，批准权在值班经理（HTTP 403）。
- 并发出餐与退款：状态迁移用条件 `UPDATE ... WHERE status=...`，先到者胜，后到者得 409——同一道菜不会既交付又全额退款。
- 退款幂等两层：审批单 `idempotency_key` 去重；批准重复提交回放原结果，支付/打印回执也按幂等键去重，绝不二次退款。

## 结构

```
backend/db.py        SQLite schema + 全语句串行锁连接
backend/service.py   状态机/催单/退菜/重做/审批/费用（所有写操作单事务）
backend/adapters.py  支付、打印模拟适配器（幂等回执）
backend/server.py    stdlib http.server JSON API + 静态页
backend/seed.py      演示数据（通过真实 Service 方法走流程）
frontend/            三屏（白/墨黑/暖红）
assets/dishes/       启动时生成的本地 SVG 演示照片
tests/test_service.py 24 个测试：并发、幂等、重复催单、角色权限、责任费用
```

## 测试

```bash
python3 -m unittest tests.test_service -v
```

覆盖：30 轮多线程出餐↔退款竞争（两种交错均真实发生、退款恒 ≤1 笔）、
退款/审批幂等回放、重复催单单队列、服务员免单/审批/改判责任被拒、
未出餐全额退款被拦截、重做链推进与错上桌费用。
